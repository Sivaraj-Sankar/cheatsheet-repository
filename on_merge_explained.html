1. What Triggers This Workflow?

The workflow fires under two conditions:

  • Pull Request Merged to main — whenever a PR is closed and the flag github.event.pull_request.merged == true is set. Simply closing a PR without merging does not trigger a build.
  • Manual trigger (workflow_dispatch) — any team member can press Run workflow in the GitHub Actions UI to kick it off without a PR. 
on:
  pull_request:
    types:
      - closed          # only when PR is closed…
    branches:
      - main            # …against the main branch
  workflow_dispatch:  # manual run via GitHub UI

2. Global Environment Variables

Two env vars are set at the top level so every job can access them. They are used to authenticate with the company's internal <artifact-registry> (e.g. Artifactory / Nexus) when pulling private Python packages during the Docker build.

Variable Source Purpose
UV_INDEX_<REGISTRY>_USERNAME GitHub Repository Variable (vars.*) Username for the private PyPI proxy
UV_INDEX_<REGISTRY>_PASSWORD GitHub Secret (secrets.*) Token/password — encrypted, never logged
uv is a fast Python package manager. The UV_INDEX_* prefix tells it to authenticate against the private registry so it can download internal company Python packages during docker build.

5. build-publish — Step-by-Step

  • Checkout

    Uses actions/checkout@v3 with fetch-depth: 0 to pull the complete git history (not just the latest commit). This is needed so that tools like git rev-parse can see all commits.

  • Get GitHub App ID from HashiCorp Vault

    Uses the company's custom action <org>/action-sre-vault-retrieve-secret to fetch the GitHub App ID from Vault at <vault-secret-path>/gh-app-action-workflow-rw. This is the GitHub App used to authenticate with GitHub APIs.

  • Get GitHub App PEM Key from Vault

    Same Vault path, different field — fetches the base64-encoded private key of the GitHub App. This key is used in the next step to generate a short-lived installation token.

  • Generate GitHub App Token

    Uses philips-software/app-token-action to exchange the App ID + PEM key for an installation token. This token grants the workflow permission to interact with repos in the <your-github-org> org (e.g. push image metadata, update deployment repos).

  • Set Short SHA Tag

    Runs git rev-parse --short HEAD to get a 7-character commit hash (e.g. a1b2c3d). This becomes the Docker image tag and is exported as steps.version-sha.outputs.sha_short for downstream jobs. 

    echo "sha_short=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT
  • Build & Push Docker Image

    Uses the company's internal action <org>/sre.actions.docker-build-push@v1.x.x to:

    • Build the Docker image from the repo's Dockerfile
    • Pass registry credentials as --build-arg so uv can install private Python packages inside the image
    • Tag the image as <your-api-name>:<sha_short>
    • Push to the company's internal container registry (Artifactory / ECR)

Both Flyway jobs reuse a shared, org-level workflow from <your-org>/<shared-workflows-repo>/.github/workflows/flyway.yml@main. DB credentials are pulled from AWS Secrets Manager using the prefix <your-secret-prefix>.

8. Deployment — How Does It Reach Kubernetes?

The dev-deploy job uses the action <org>/sre.actions.deploy-dispatcher@v2.x.x. This is a GitOps-based deployment action. Here's what happens internally:

  • dispatch-dispatcher finds the GitOps repo

    It locates the Kubernetes deployment configuration repository for the <your-team-name> team and the <your-app-short-name> application.

  • Patches the image tag in the config file

    It updates the value at the YAML path .<company>-deployment.image.tag in the deployment config (e.g. a values.yaml or .<company>-deployment.yaml) to the new short SHA. 

    # Before
<company>-deployment:
  image:
    tag: abc1234

# After (patched by the action)
<company>-deployment:
  image:
    tag: a1b2c3d  ← new SHA from this build
  • Commits & pushes the change

    The action commits this tag bump to the GitOps repo using the GitHub App token.

  • ArgoCD / Flux detects the change

    The company uses a GitOps controller (likely ArgoCD) watching the GitOps repo. It detects the new commit, pulls the updated image tag, and instructs Kubernetes to perform a rolling deployment of the new image.

Result: The new Docker image <your-api-name>:<sha> is rolled out to the dev Kubernetes cluster with zero manual steps.
