How your merged code travels from GitHub → Docker image → Kubernetes pod  |  Reconstructed from on_merge.yml

Part 1 — What is GitOps?

GitOps is a deployment philosophy where Git is the single source of truth for what should be running in your infrastructure. Instead of running kubectl apply or helm upgrade manually, you commit a change to a Git repo and an automated controller reconciles the cluster to match.

Traditional Deploy vs GitOps Deploy

Traditional (Push) Deploy

  • CI pipeline runs kubectl apply directly
  • Cluster state lives only in the cluster
  • Hard to audit — who changed what, when?
  • Rollback = re-run old pipeline
  • Secrets & configs drift over time

GitOps (Pull) Deploy

  • CI only updates a config file in Git
  • Cluster state is declared in Git — always auditable
  • Every deploy is a Git commit — full history
  • Rollback = git revert
  • Cluster self-heals if someone manually changes it
Key rule: No one touches the cluster directly. Every change goes through Git first. The cluster pulls its desired state from the repo — it is never pushed to.

Part 2 — What is a Config Repo?

A config repo (also called a GitOps repo or deployment repo) is a separate Git repository that contains only Kubernetes configuration — no application source code, no business logic.

  • App repo (<your-api-name>) — holds your Python code, Dockerfile, tests. This is what developers work in.
  • Config repo — holds Helm values, image tags, replica counts, env vars, resource limits. This is what ArgoCD reads.

Why separate repos?

App Repo changes when…

  • A developer pushes new features or bug fixes
  • Dependencies are upgraded
  • Tests are added or changed

Config Repo changes when…

  • A new Docker image tag is released ← this pipeline
  • Replica count is scaled up/down
  • Environment variables change
  • Resource limits are tuned
In your pipeline, the deploy-dispatcher action opens and edits the config repo — it bumps the image tag value and commits it. ArgoCD then sees that commit and deploys the new image.

Part 3 — What is ArgoCD? What is Flux?

Both are GitOps controllers — software that runs inside your Kubernetes cluster and continuously watches a Git repository. When it detects a change, it applies that change to the cluster automatically.

ArgoCD likely used here

  • Runs as pods inside Kubernetes
  • Has a visual web UI — shows sync status per app
  • Polls the config repo every ~3 minutes
  • Can show diff between Git and live cluster
  • Supports manual sync + auto-sync modes
  • Each app is declared as an Application CRD

Flux

  • Also runs inside Kubernetes
  • More CLI-oriented, no built-in UI
  • Uses GitRepository + Kustomization CRDs
  • Slightly more lightweight
  • Both achieve the same GitOps outcome

  pullPolicy: Always

  enabled: true

📄 argocd/applications/<app>-dev.yaml
# ArgoCD Application CRD — tells ArgoCD what to watch and where to deploy.
# ArgoCD reads this and continuously syncs the cluster to match the config repo.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: <your-app-short-name>-dev
  namespace: argocd
spec:
  project: <your-team-name>

  source:
    repoURL: https://github.com/<your-org>/<company>-gitops-config
    targetRevision: main
    path: apps/<your-team-name>/<your-app-short-name>/dev  # ← watches this folder

  destination:
    server: https://kubernetes.default.svc
    namespace: <your-team-name>-dev         # K8s namespace where pods land

  syncPolicy:
    automated:
      prune: true       # delete removed resources automatically
      selfHeal: true    # if someone manually changes the cluster, revert it
    syncOptions:
      - CreateNamespace=true
📄 charts/<app>/templates/deployment.yaml
# Kubernetes Deployment template. Helm fills in {{ .Values.* }} at deploy time.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Values.app | default "<your-app-short-name>" }}
  namespace: {{ .Release.Namespace }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Values.app }}
  template:
    spec:
      containers:
        - name: {{ .Values.app }}
          image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
                    # ↑ this is where the patched SHA gets injected into the pod spec
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          envFrom:
            - secretRef:
                name: {{ .Values.secrets.awsSecretName }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

Part 6 — Key Terms at a Glance

TermWhat it means in this context
GitOps Using Git commits as the trigger and source of truth for all deployments
Config repo A separate repo holding only Kubernetes/Helm config — no app code
ArgoCD A Kubernetes controller that watches the config repo and syncs the cluster to match it
deploy-dispatcher <Company> SRE action that bumps the image tag in the config repo on every merge
image-tag-path The YAML dot-path inside the config file that holds the Docker tag — .<company>-deployment.image.tag
Helm Kubernetes package manager — chart templates + values files = rendered K8s manifests
Rolling update Kubernetes replaces pods one-by-one with the new image — zero downtime
Self-heal ArgoCD detects manual cluster changes and reverts them to match Git
Application CRD ArgoCD's custom resource that maps a Git folder to a K8s namespace
